## A narrower next target: materializing attention slices

The comparison matches `/layers.i/self_attn/Slice_1` and `Reshape_7` together
for every layer from 0 through 23. Lokad takes **2.961947s**, ORT **0.024002s**;
the excess is **2.937945s**, about **4.0% of a complete Lokad request**. Matching
the pair avoids attributing a saving to moving a copy between operators.

Original and optimized model edges, outputs and constant values agree. Both
engines merge identical constants, so their names differ; comparison checks
the values rather than requiring identical constant names. Native runtime
shapes cover every corpus clip, with 19 distinct encoded lengths from 51 to
225. At encoded length T, the pair performs:

1. Slice `[1,8,2T,T]` on axis 2 from 1 to the end, producing `[1,8,2T-1,T]`.
2. Reshape that result to `[1,8,T,2T-1]`.

The selected Lokad source returns a `TensorSlice` view. Its `Reshape` calls
`Clone`, which calls the generic `Tensor.ToDenseTensor`: a coordinate iterator
reads and writes each element individually. The dense result can then be
reshaped without another copy. In the pinned ORT source, Slice uses
`CopyContiguousInnermostAxes`, which uses `memcpy` for contiguous numeric blocks;
Reshape is registered with input/output aliasing.
This explains why copying falls under different operator names.

The [subsequent actual-layout capture](../slice-materialization-results/layouts-20260924.md)
confirms all 1,920 layouts, and the
[isolated copying candidate passes its tensor contracts](../slice-materialization-results/qualification-20260924.md).
Full-model and performance gates remain. The original diagnostic interpretation follows.

The source mechanism is a hypothesis about the observed cost, not a sampled
proof of each runtime tensor's concrete layout. **The next gate is to confirm
that layout and the applicable contiguous spans in the actual model.** There
are eight contiguous retained regions separated by the removed first row of
each head. Treating the entire slice as one contiguous alias would be wrong.
If the immediate parent is dense and row-major as the graph/source indicate,
materialization can copy those regions in bulk while preserving independent
storage. Nested, reversed or stepped layouts must keep a correct fallback.

The single proposed experiment is a guarded bulk-copy path for this
materialization, preserving all arithmetic and ownership behavior. Its
optimistic observed ceiling is 2.94s, not a promised application saving. Reject
the hypothesis if actual layout does not qualify, the complete pair does not
get materially cheaper, or the complete application misses its unchanged
3% gain/no-clip-over-5%-regression gates. No padding, Where or matrix kernel
change belongs in this candidate.

Evidence: [24 matched pairs](slices-20260924.csv),
[shape/source identities](slice-observations-20260924.json), and
[comparison code](../managed-phase-amd/compare_slices.py). The first metadata
check refused differing constant names; checking their original values resolved
the optimizer's deduplication. No inference was repeated.

## Other observed costs and limits

Lokad encoder Conv consumes 9.464s, Where 3.263s, Pad 2.893s and Sigmoid 2.375s.
These are useful remaining leads, **not complete matched ORT comparisons**:
native convolution/layout and activation fusions can move work across nodes.
Convolution and fused activation groups still need that reconciliation before
selecting a change. Earlier padding and selection trials retain their original
failed controls and rejection reasons. No unchanged retry follows from this
profile.

The independent prepared-recurrence candidate already passed its full
application gate with a 4.737% gain; it remains unintegrated pending shared-model,
root, suite and package checks. Its result does not qualify this new hypothesis.
