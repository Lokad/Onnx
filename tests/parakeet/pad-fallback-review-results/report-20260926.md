# Padding fallback: what the retained comparisons establish

The next justified measurement is one unchanged-binary diagnostic with a
time-based warmup and recorded compilation state. Another padding implementation
or compiler flag is not selected. The existing M47 and M49 screens remain
rejected, and the release comparison remains 53.107381 seconds versus ORT's
39.207695 seconds.

The exact Parakeet encoder contains 48 constant, nonnegative last-axis Pad nodes.
For these inputs, pinned ORT `PadImpl<uint32_t>` copies contiguous innermost
blocks and fills their borders. Lokad's current `PadCore<float>` fills its output
and translates every source element across dimensions with division/remainder.
The [current attribution](../owned-batch-isolation-profile-results/diagnosis-20260925.md)
measures 2.880430 versus 0.050175 seconds, bounding the application opportunity
at roughly 5%. This ORT route follows the executed node descriptors and pinned
source; the internal native Pad leaf has not been independently sampled.
[Pinned ORT implementation](https://github.com/microsoft/onnxruntime/blob/2e2543fbe9fae542f921d47a72d21d5a4ef0b710/onnxruntime/core/providers/cpu/tensor/pad.cc).

The rejected M47 helper implements that block-copy idea for eligible inputs and
routes cropping, outer padding and reflection to the unchanged generic method.
Its eligibility checks precede materialization and allocation. Source inspection
does not identify new heap allocation on the fallback branch. The observed
88-byte allocation-counter difference includes instrumentation and cannot be
assigned to the dispatcher without more evidence.

The retained runtime diagnostic captures all 18,720 calls. Its candidate completes
the last call at 2.299 seconds from trace origin, versus 22.983 for the selected
binary. Both call every case 600 times before 180 labeled measurements; this
count does not establish equivalent compilation state.

| Trace observation | Selected | M47 candidate |
|---|---:|---:|
| Fully optimized public Pad available | 4.806502 s | Not loaded before the last call |
| Fully optimized PadCore available | 4.844587 s | Not loaded before the last call |
| First measured cropping call | 22.670103 s | 1.935160 s |
| First measured outer-padding call | 22.789637 s | 2.080307 s |
| First measured reflection call | 22.945343 s | 2.258519 s |

The candidate has optimized loop versions, including its constant loop from the
first cropping call. Its public Pad and dispatcher have no fully optimized
whole-method load in this trace. Availability is not proof of which code every
invocation executed. The old trace contains no tiering pause/resume events, so
it does not establish the exact delay interval in these processes.

.NET 10.0.8's default call-counting delay is 100 milliseconds, with a configured
single-processor multiplier of ten. New method activity can extend the delay;
the background worker waits before enabling call counting and promotion.
This source mechanism is consistent with the observed short candidate lifetime,
but is not a direct recording of that process's pending promotion state.
[Runtime defaults](https://github.com/dotnet/runtime/blob/v10.0.8/src/coreclr/inc/clrconfigvalues.h),
[tiering implementation](https://github.com/dotnet/runtime/blob/v10.0.8/src/coreclr/vm/tieredcompilation.cpp).

The earlier M49 annotation is important counterevidence, but it does not close
this question. The reviewed binary changes the implementation flag on PadCore
alone, from 0 to 512; public Pad and the dispatcher retain ordinary flags.
`AggressiveOptimization` bypasses ordinary tiering and its dynamic PGO, so it
does not reproduce the selected method's warmed profile-guided compilation.
There is no compilation trace for M49 in the reviewed evidence.
[Microsoft's MethodImplOptions contract](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.methodimploptions?view=net-10.0).

M49's two candidate cropping process means are approximately 162.493 and
151.609 microseconds. Their individual consecutive 60-call block means are
150.173, 163.747, 173.558 and 150.291, 150.050, 154.485 microseconds.
All six blocks stay in the result. The variability does not prove a GC or JIT
cause; M49 did not record those associations. The original M47 diagnostic also
shows that GC suspension alone cannot explain its fallback differences.

The follow-up must distinguish two explanations: residual fallback overhead
persists after ordinary optimization, or the old short protocol compares
materially different compilation histories. Use the original selected 521bae17
and rejected 060950a1 products, no runtime flags, the same twelve cases and the
unchanged 600/180 suffix with all original output and ownership checks. Before
that suffix, rehearse the complete case census until at least ten seconds have
elapsed after the first complete rehearsal. Ten seconds is fixed before running,
exceeds the retained 4.845-second whole-method load observation and is not chosen
from a passing latency ratio. It is a bounded probe, not a guarantee of tiering.

Record every prefix call and the original suffix. Interpret the fallback
comparison only if the trace establishes fully optimized Pad/PadCore availability
in both products and PadDispatch in the candidate before the measured suffix,
with subsequent relevant loads reported. If that condition is absent, report
the diagnostic as inconclusive; do not increase the warmup until a score passes.
If fallback regressions persist, this padding proposal remains rejected. Even a
favorable diagnostic cannot promote a product: the original repeatability,
numerical, ownership, shared-model and complete-application gates still apply.
