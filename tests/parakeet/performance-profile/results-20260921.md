# Parakeet: complete graph attribution and prepared-weight census

Encoder matrix multiplication is the first measured Parakeet optimization
target: **60.4% of profiled graph time**, versus 7.3% for decoder LSTM. Pyannote
remains first in the program. This local diagnostic result does not change the
matched Microsoft ORT baselines.

## Workload and result

Windows i7-14700KF, logical CPU 2 inherited before CLR startup, normal .NET
10.0.12 settings, FP32 Parakeet TDT 0.6B V3. The twenty clips contain 3,412,240
samples / 213.265 seconds and require 1,200 decoder calls per complete pass.
Exact frozen production Core `d1f86a73`, Data `e7fe1668`, consumer `1193ca4a`.
No product arithmetic changes or native runtime calls occur in this experiment.

Across clips, encoder graph time ranges from 1.780 to 3.808 seconds, decoder

combined graph time. These ranges describe different clips, not repeated-trial

The separate twenty public `Transcribe` controls total 62.228 seconds and all
match the native public reference. These are one-pass controls including startup
effects, without dedicated warmup or a simultaneous ORT measurement. Graph
timers cover `GraphExecution.Execute`; resets, captures, hashing and external
ownership checks are outside them. Public and graph instruments have different
overheads: their difference is not API overhead, and neither may be combined
with historical ORT times for a new ratio.

## Correctness and audit

One complete unprofiled pass and one wall-profiled pass contain 2,480 graph
calls, 12,160 input arrays, 9,760 output arrays and 57,662,752 captured values.
Every input and output retains identical bits between passes. The independent
auditor checks raw bytes, shape, dtype, hash and finite values, then reconstructs
every greedy token/duration decision, selected encoder frame and accepted
recurrent state, including old-state retention on blanks. All forty traced and
twenty public results match the original ORT 1.29 public reference.

Every profiled call contains its complete nodes exactly once: 34 frontend,
2,856 encoder and 29 decoder nodes. Integer clocks must be ordered, nonoverlapping
and inside the graph call; aggregation uses rational arithmetic. Held outputs
and caller PCM remain unchanged. Seven capture layouts and nonfinite refusal
pass. Two adversarial audit tests reject corrupted clocks, operators, states,
frames, logits and truncated trajectories.

This proves instrument neutrality and public agreement. The existing three
Windows duration-logit failures at the strict `1e-4` tolerance, maximum absolute
error `0.0002321004867553711`, remain open. There is no new tensor-native verdict.

## Actual prepared weights

A separate consumer loads the same six model assets and exact Core/Data,
creates Memory-policy contexts and inspects actual mappings without inference.
Every graph/node/initializer descriptor matches the qualified trace. Encoder
preparation fills its 268,435,456-byte budget with 37 of 217 constant MatMul
weights. Decoder preparation holds all three constant weights, 25,246,720 bytes,
within its 64 MiB budget. Frontend preparation has a zero budget.

| Encoder B shape `[K,N]` | Constant weights | Prepared weights | Profiled node seconds |
|---|---:|---:|---:|
| `[1024,1024]` | 120 | 28 | 9.613 |
| `[1024,4096]` | 48 | 9 | 12.340 |
| `[4096,1024]` | 49 | 0 | 12.794 |
| Dynamic B | 72 nodes | 0 | 0.838 |

Nodes with prepared weights account for 3.967 seconds, or 11.1% of encoder
MatMul time. Mapping presence does **not** prove packed kernel dispatch: Lokad
also checks runtime options, FMA and row-count eligibility. This census does
not measure packing time separately or attribute the native gap to packing.

`GraphPacking.FitsPackBudget` requires `K < 4096`, excluding all 49 weights
shaped `[4096,1024]`; per-graph residency limits the other shapes.
`ResolvePackedKernel` requires even rows or an exact multiple of three.
Unmapped large operations can still pack on each call. The inspected source
matches the frozen product after newline normalization.

## ORT source and next experiment

The audio baseline uses ORT 1.29.0; source inspection pins commit
`2e2543fbe9fae542f921d47a72d21d5a4ef0b710`. Its FP32
[MatMul preparation](https://github.com/microsoft/onnxruntime/blob/2e2543fbe9fae542f921d47a72d21d5a4ef0b710/onnxruntime/core/providers/cpu/math/matmul.cc)
handles constant B through `GemmPackBFp32`. That
[helper](https://github.com/microsoft/onnxruntime/blob/2e2543fbe9fae542f921d47a72d21d5a4ef0b710/onnxruntime/core/providers/cpu/math/gemm.cc)
accepts rank-two weights and asks MLAS for packed storage. The
[SGEMM implementation](https://github.com/microsoft/onnxruntime/blob/2e2543fbe9fae542f921d47a72d21d5a4ef0b710/onnxruntime/core/mlas/lib/sgemm.cpp)
traverses output-column and reduction blocks and reuses packed B. These are
verified mechanisms, not a trace of the installed wheel's dispatch.

Next compare packing-inclusive wide encoder MatMul kernels on the observed
shapes and row counts before changing preparation budgets. Separate reduced
packing from better reuse during multiplication; retain memory costs, tails
and fallback. Any change needs the full managed trajectory at the original
numerical tolerance, followed by complete application timing. A higher memory
budget alone is not a kernel gain. Parakeet's one-step hidden-size-640 LSTMs
remain a later target; pyannote's recurrent admission does not cover them.

## Resources and preserved failures

The successful trace has 513 samples and peaks at 8,327,315,456 bytes RSS under
its 8 GiB ceiling. The public successor has 255 samples and peaks at
9,191,219,200 bytes under its declared 12 GiB ceiling. Public preflight requires
14 GiB available memory; trace preflight requires 10 GiB. Other limits remain
1,800 seconds, at least 1 GiB available memory and 20 GiB free disk, and at most
1 GiB capture files. All four process identities are verified terminal. The
preparation census has five samples, 2,689,949,696-byte peak RSS and terminal
supervisor/worker identities.

Three failed attempts remain preserved. The first combined worker completed
both trace passes but crossed 8 GiB during public controls, peaking at
8,636,985,344 bytes. After the corrected trace succeeded, the first separate
public worker encountered a Windows progress-file replacement error after five
controls. Its public-only retry crossed the unchanged 8 GiB guard at
8,723,816,448 bytes. Neither partial public attempt has a complete result.
The final explicit successor uses 12 GiB, consistent with earlier public runs
exceeding 8 GiB, and leaves the successful trace unchanged. Metadata
`PermissionError` writes alone retry for at most one second. No forced GC,
global runtime override or automatic inference retry is introduced.
