# Parakeet arithmetic trial: correctness passes, timing controls fail

All six processes completed their original workload: **480 requests pass**,
including two fresh Microsoft ORT runs. All 4,879 resource observations pass.
The predeclared repeatability controls fail for production and the candidate,
so **this trial does not establish a speedup or select a performance candidate**.
The separately qualified numerical improvement remains valid.

## Complete observed measurements

Windows i7-14700KF, CPU2, normal .NET 10.0.12 and ORT 1.29.0. Both managed
roles use the original 256 MiB encoder packing budget, identical Data and the
byte-identical original consumer. Only Core differs: production `d1f86a73`,
corrected partial-sum candidate `f2c292cb`. The workload is all twenty clips,
totaling 213.265 seconds of audio.

The cause of the managed timing variation is **unassigned**. These records
contain sampled memory and application timings, not GC pause or allocation
attribution. They do not justify blaming GC, a particular foreign process or
the arithmetic itself. The unrelated workstation workload was preserved.

## Consequence and evidence

This closes the prospective trial with `passed:true` for its audited
correctness/resource evidence and **`attribution_valid:false`**,
`selected_for_amd:null` for its performance verdict. All seven process
identities are terminal. There is no unchanged local timing retry or change
to accepted benchmark tables, production defaults or the frozen AMD queue.
Pyannote retains priority after the live e5 campaign.

Before another local comparison, investigate managed allocation/pause behavior
under the original complete application workloads using separate diagnostic
consumers and unchanged conformance checks. That investigation must not be
presented as matched performance evidence or presume the cause of this failure.
