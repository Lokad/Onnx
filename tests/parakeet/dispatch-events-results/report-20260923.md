# Parakeet matrix runtime diagnosis

The traces identify different compilation schedules as a concrete mechanism to
address next. They do **not** establish the cause of every previous slowdown or
qualify either rejected candidate. M40 and M41 remain rejected. The current
release remains **76.172826 seconds versus ORT 39.782592 seconds** for the
twenty-clip Parakeet workload; no product code or benchmark row changed here.

Two fresh diagnostic processes ran the same 21 fixtures in order, with 120 calls
each. All 5,040 calls completed; full outputs at both phase endpoints for every
fixture, input immutability and output guards passed. All 10,080 begin/end
markers match their original clocks, process and native thread. Both raw traces
report zero lost events. Compute and all worker threads used CPU 2; collection
used CPU 0. Normal runtime tiering remained enabled.

## What the events show

These are the parser-reported optimized method-load events. An event identifies
when a body became available; it does not by itself prove which body executed
every subsequent instruction. Fixture and iteration numbers are zero based.

| Method | Current product | Rejected M41 product |
|---|---|---|
| Packed two-row consumer, optimized Tier 1 | Fixture 6, iteration 57 | Fixture 7, iteration 7 |
| Unpacked row fallback, optimized Tier 1 | Fixture 6, iteration 30 | Fixture 16, iteration 72 |
| General dispatcher, optimized Tier 1 | Fixture 6, iteration 29 | Fixture 7, iteration 6 |

Fixture 6 is M167/reduction 1024/output 4096, the case that failed the earlier
performance gate. The candidate loads instrumented versions of its dispatcher
and packed consumer during iteration 94; further on-stack replacement and a
batch of background compilation overlap iterations 95–97. The recorded call
durations are 26.525, 36.892, 29.973 and 28.196 ms respectively. Compilation also
includes the diagnostic consumer and runtime helpers, so observer effects are
visible and these times must not replace the unprofiled screen.

The current M48/1024/1024 tiled consumer loads optimized Tier 1 during iteration
61, overlapping that 6.169 ms call. Other slower calls in the same fixture
(iterations 92, 111 and 112) overlap neither a recorded compilation interval nor
a GC pause. Their cause remains unresolved. This diagnostic does not explain
away the earlier repeatability failure.

There are **no GC collection-count changes inside any matrix call**, and none
of the 16 current / 14 candidate GC or GC-preparation suspension intervals
overlaps a call boundary. Most suspension events have reason `SuspendOther`
(30,391 / 17,820); they must not be counted as GC collections. Allocation-counter
deltas are preserved: these are approximate process-wide observations around
the call and markers, not precise allocation attribution to a matrix kernel.

## Stack and event accounting

All exported stack intervals reconcile, including intervals outside calls and
the additional finalizer-thread profile. Inside calls, the exporter represents
39,649.630 current / 23,056.288 candidate milliseconds of sampled thread time.
These are instrumented observations with different executed paths, **not CPU
time measurements or a new performance comparison**.

For fixture 6's recorded phase, sampled packed-consumer attribution totals
1,011.773 current / 1,087.428 candidate ms; the unpacked-row attribution totals
41.408 / 75.656 ms. These associations support investigating when these kernels
are optimized. Inlined packing is not separately visible in the current
product's samples; unattributed work stays in `other`. No absent stack frame is
treated as zero work, and all intervals remain in the accounting.

The initial typed CLR exporter missed 50 current / 45 candidate runtime records
from its JSON while retaining them in the raw traces and provider census. An
offline exporter then preserved **all 168,906 / 104,729 records**, including
unrecognized events, raw payload bytes, sample records and rundown. Its census
matches the original trace exactly, and every previously exported typed/custom
record matches field for field. No inference was rerun. Raw payload access uses
TraceEvent's documented-in-source [`EventData()` API](https://github.com/microsoft/perfview/blob/main/src/TraceEvent/TraceEvent.cs).

original frozen tools and outputs remain intact.

The next source experiment should compile the small set of tight matrix kernels
in optimized form on first use, combined with short-projection packing. This
would address dependence on earlier shapes and delayed kernel tier changes
without altering measurement policy. It requires its own normal build, numerical
checks, native-code review and unchanged performance gates. It cannot admit M41
retroactively. End-to-end Parakeet and ORT comparison follows only if those gates
pass; the other supported workloads remain regression checks.
