# Parakeet padding: actual application order and compilation history

The next optimization should follow an explained execution difference. Current
release attribution identifies encoder padding at 2.880430 seconds against the
retained ORT profile's 0.050175 seconds. ORT's applicable constant-padding path
copies contiguous blocks; Lokad's generic path translates each source index
across dimensions. The 48 encoder pads use nonnegative zero padding on the final
axis. This is a specific algorithmic discrepancy with a roughly 5% application
benefit ceiling, rather than a reason to sweep unrelated matrix kernels.
See the [current attribution](../owned-batch-isolation-profile-results/diagnosis-20260925.md)
and [pinned ORT implementation](https://github.com/microsoft/onnxruntime/blob/2e2543fbe9fae542f921d47a72d21d5a4ef0b710/onnxruntime/core/providers/cpu/tensor/pad.cc).

One diagnostic reused selected Core 521bae17 and rejected M47 Core 060950a1, with
the same retained Data observer. These are older products. Current release
performance remains **53.107381 seconds versus ORT 39.207695**. Neither diagnostic
clock below replaces that comparison, and the rejected proposal is not admitted.

| Instrumented work, seconds per 20-clip corpus | Selected | Rejected M47 |
|---|---:|---:|
| Complete requests | 75.391536 | 72.277576 |
| Encoder padding | 2.882177 | 0.194988 |
| Actual frontend reflection padding | 0.036414 | 0.036068 |

Encoder padding uses 93.2347% less time in this observation. Frontend reflection
is similar in aggregate; the first measured pass is 0.034848 versus 0.037315
seconds. There is one instrumented process per binary, no uninstrumented control
and no performance admission. The complete request difference cannot all be
attributed to padding from this pair alone.

The compilation histories differ substantially:

| PadCore compilation event | Selected, seconds from trace origin | M47, seconds from trace origin |
|---|---:|---:|
| Initial compilation | 0.996 | 0.995 |
| First optimized loop version | 0.999 | 0.998 |
| Instrumented method version | 9.710 | 115.809 |
| Fully optimized method version | 15.652 | 224.071 |

The selected fully optimized method is available before the fourth warmup
request. M47's becomes available before request 62, in the third measured pass.
The generic fallback receives far fewer calls after the encoder bypasses it.
Both processes already have optimized loop versions during their first frontend
request. Method-load events establish available code, not which version every
invocation executed. They expose a compilation-state difference that needs to
be considered when interpreting the old synthetic fallback comparisons.

All 160 complete requests match native/public expectations and each other,
including decoder decisions and ownership checks. The original phase auditor
reconciles every graph and operator interval, including 7,840 Pad calls. Both
compiled binary checks pass: the known Pad dispatcher is the only changed
existing Core method; the original PadCore and implementation flags are exact.
The consumer preserves its other 163 methods. All 12 runtime jobs and 2,432
resource observations pass, with peak owned RSS 9,417,433,088 bytes.

The original diagnostic protocol **fails its named request-marker check**.
Both traces contain zero of the expected 160 legacy markers, although all 161
scalar clock anchors per process are present and EventPipe reports zero loss.
That failure is retained at closure
`0f7c5cd1c4d022aaf72ffc1c8f8a764336e65bad171d0435e5f7892871004020`.

Source inspection explains the filter mismatch: the compiled legacy Boundary
method uses the EventSourcePrimitive array overload. The runtime's varargs path
checks the descriptor's session-augmented keywords against the configured mask;
this diagnostic used 0x1, while the earlier application tracer used all keywords.
Scalar clock writes use the other overload and were recorded. This is a
source-supported explanation, not a separate runtime reproduction.
[EventSource v10.0.8](https://github.com/dotnet/runtime/blob/v10.0.8/src/libraries/System.Private.CoreLib/src/System/Diagnostics/Tracing/EventSource.cs),
[EventProvider v10.0.8](https://github.com/dotnet/runtime/blob/v10.0.8/src/libraries/System.Private.CoreLib/src/System/Diagnostics/Tracing/EventProvider.cs).

A separate read-only review reconciles every scalar counter's raw bytes,
decoded value, native thread and placement around each request. The common clock
offset intervals are 6.774 and 6.835 microseconds wide. No named marker is invented
and the failed original gate stays failed. The timing associations above use
these independently checked anchors and the unchanged phase records. Four
rejection tests cover missing anchors, wrong requests/threads and preservation
of the original failure. Independent review closure:
`dc18a3c23ab1066a10e79e19b127ceb4dc25d0a290f38cee7f3ec6a558c323a3`.

The next step is to reconcile the original synthetic cropping and outer-padding
failures with their retained compilation events. If their measured blocks
compare different compilation states, define a corrected warmup protocol
prospectively and verify it once using the unchanged binary pair. Do not choose
a warmup count by whether a speed gate passes. If regressions remain under
comparable compilation state, keep this proposal rejected. These observations
do not justify another padding, compiler-flag or matrix-kernel variant.
