# Parakeet recording qualification — 2026-09-19

The new `TranscribeRecording` API and CLI `--model-type parakeet --recording`
match the native application on the retained Windows cases, including a
ten-minute repeated-speech request. Long-recording accuracy remains limited:
adding leading silence causes substantial deletions in one constructed case,
equally in both engines. [Usage and policy](README.md) explain boundaries,
work limits and partial results.

Implementation source is `f568132f63e375a43686dc83c5c983f905d2d493`.
The campaign froze its executable source and DLLs before inference on Windows
i7-14700KF, logical CPU 2, .NET 10.0.12, SDK 10.0.204. Microsoft ORT 1.29.0 uses
one intra-op/inter-op thread, sequential execution and CPU graphs with all
optimizations enabled. Both engines use the same pinned FP32 assets and PCM.
No core arithmetic, defaults or numerical tolerances changed.

## Application and accuracy

All ten sequential public recording calls match native text, every token,
encoder-frame position, duration prediction, decoder-call count, boundary,
stop reason and committed duration. These cover nine cases and a final repeat.
The native generator independently runs the original pinned onnx-asr decoder
for all 38 nonsilent windows. Managed inference carries its own recurrent state
and does not load native ORT.

| Constructed recording | Duration | Windows | Word errors / reference words | WER |
|---|---:|---:|---:|---:|
| Six utterances joined with 0.3 s silence | 69.455 s | 3 | 4 / 160 | 2.50% |
| Same recording with 2.37 s leading silence | 71.825 s | 3 | 18 / 160 | 11.25% |
| Same recording with +0.02 DC offset | 69.455 s | 3 | 84 / 160 | 52.50% |

These share the same speech and are **correlated diagnostics**, not three
independent accuracy samples. Labels and normalization were fixed before
inference. Every error remains in [observations-20260919.json](observations-20260919.json).
The connected case has three substitutions and one insertion. The shifted case
has two substitutions, fifteen deletions and one insertion. Its first window
omits the end of an utterance despite native/managed agreement. The DC-offset
case has four substitutions, seventy-nine deletions and one insertion. It
forces hard cuts but also alters the waveform, so it cannot isolate hard-cut
accuracy. No boundary threshold was adjusted after seeing these outcomes.

Connected boundaries are at 26.595 and 55.060 seconds. Shifted boundaries are at
28.965 and 57.430 seconds, exactly 2.37 seconds later. Both use quiet boundaries;
the DC-offset case uses hard cuts at 30 and 60 seconds. The leading-silence
failure therefore persists even when the quiet boundaries translate with the
waveform. This establishes a limitation to investigate, not its numerical cause.

With a two-token limit, the first partial window remains inspectable, while
top-level text is empty and processed duration is zero. A one-window limit
commits 26.595 seconds. The actual CLI agrees exactly on the complete connected
recording and the token-limited request, including stderr behavior. Sixteen
invalid/canceled-request checks pass with subsequent successful recovery.
Two concurrent silence requests, retained-result immutability and input
preservation pass. Empty input, a tiny padded tail and ten minutes of digital
silence also match native decisions.

## Finite resource observation

The 600-second stress input cyclically repeats the connected recording. It
completes all 22 windows and 2,695 emitted tokens in **173.9354481 seconds** of
public API time, including features and decoding, excluding model load and
external validation. Model construction took 1.0584197 seconds. This request
follows the shorter cases in one process; it is not a dedicated latency trial
or independent long-conversation accuracy test.

Across the full managed sequence, sampled process-group peak RSS is
**13,272,190,976 bytes** (13.27 decimal GB); process-reported peak working set is
13,362,720,768 bytes. Sampling every 0.5 seconds can miss transient peaks. The
supervisor's 20 GiB / 1800-second per-worker guards were not reached. No forced
garbage collection was used. The first connected request takes 22.492 seconds
and its final repeat 18.230 seconds; both return identical decisions.

Native reference time includes an additional original-decoder run and validation.
It is **not a matched ORT latency baseline**. Use the separately measured
[short-audio ORT comparison](../../audio/comparison/results-20260919.md) for
performance ratios. This local finite sequence establishes neither an indefinite
memory ceiling nor AMD recording qualification.

## Validation and retained evidence

The independent auditor verifies source/model/binary/input identity, all
application fields, contiguous audio coverage, partial-result semantics,
word/character scoring, CLI outputs, process affinity, sampled memory and
termination of every worker and console child. Its tests cover sixteen altered
result contracts plus infinity-label normalization. Final full regression
suites pass **3,003 backend tests** (93 expected ISA skips) and **342 tensor
tests**, using exactly the same Core/Data DLLs as the recording replay.

Two initial validation failures are retained. The tensor suite rejected optional
parameters in a new test helper; explicit overloads fixed it, followed by both
full passing suites. The first auditor expected the label `Infinity`, whereas
this runtime's current culture emitted `∞`; only label normalization changed.
The failed auditor source/log and original test logs remain alongside the final
evidence. Product code and model outputs did not change during these corrections.

Raw artifacts are under `artifacts/parakeet-recording-20260919`, including frozen
source/binaries, native and managed results, process samples, CLI output,
initial failures, final tests, independent audit and closure receipt. All four
workers ended successfully. No VM job was started. Successful writers are closed;
reproduce into fresh destinations using the [recipe](README.md).
