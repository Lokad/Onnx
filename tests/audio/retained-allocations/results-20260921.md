# Retained audio allocation and collection counters

**Pyannote allocates about 5.20 GB per complete 30-second request and 146.4 GB
per ten-minute meeting.** These are cumulative managed allocations, not resident
memory. The exact candidate source creates new embedding execution contexts for
each window, giving a concrete reuse hypothesis to test before further kernel work.

This analysis executes no model. It verifies **25,231 unique evidence files**
from four closed experiments and retains all **3,047 observations**: 2,855 with
allocation totals and 2,835 with collection counters. An independent check
compares every derived observation with its original row. Existing Microsoft
ORT baselines, numerical limitations and timing verdicts remain unchanged.

already recorded these counters around the original complete public calls.
The candidate is Core `469cb2d6`, Data `e7fe1668`, .NET 10.0.12, Windows CPU2.
The separate [natural meetings](../../pyannote/optimized-meetings/results-20260921.md)
use the same qualified candidate. GB below means 1,000,000,000 bytes.

| Dialogue, 30 s | 6 measured | 5.1996–5.2058; mean 5.2013 | 15–22 |
| Dialogue, first 10 s | 6 measured | 0.2503–0.2534 | 0–2 |
| Dialogue, middle 10 s | 6 measured | 0.2503–0.2513 | 0–2 |
| Dialogue, last 10 s | 6 measured | 0.2503–0.2550 | 0–2 |

The 30-second request has 21 overlapping analysis windows, each ten-minute
meeting has 591, and each ten-second crop has one. Both meetings allocate
approximately **247.7 MB per window**, close to the short-request rate. This
supports investigating repeated per-window work. It does not identify which
operations allocated those bytes or how much latency GC caused. All eight
managed warmup requests and all 32 native requests from the comparison are
also retained; native managed-allocation counters are unavailable, not zero.

### Source evidence and the next experiment

Seven exact source files were checked against the candidate's original
qualification receipt. They match the working source except for newline
encoding. The source shows:

- [Community1Diarizer.Diarize](../../../src/Lokad.Onnx.Data/Community1Diarizer.cs)
  creates one segmentation context per request and resets it between windows.
  It calls `WeSpeakerEmbedder.ExtractPipeline` separately for every window.
- [ExtractPipeline](../../../src/Lokad.Onnx.Data/WeSpeakerEmbedder.cs) creates
  new encoder and projection contexts on each call. Its `finally` resets them;
  the method returns owned embedding vectors and retains neither context.
- [GraphExecution](../../../src/Lokad.Onnx/GraphExecution.cs) gives explicit
  contexts independent released-buffer caches. Reuse is on by default.
  [Reset](../../../src/Lokad.Onnx/ComputationalGraph.cs) clears bindings but
  preserves this cache; it does not force a collection unless explicitly asked.
- [ReleasedBufferCache](../../../src/Lokad.Onnx/ReleasedBufferCache.cs) is
  bounded at 128 MiB and 256 arrays by default. Only already-released arrays
  are retained; graph outputs and other live arrays cannot be adopted.

**Inference:** keeping the embedding contexts across windows within one public
request may reduce repeated allocation while preserving owned results. Its
benefit and memory cost are not yet measured. Do not infer that all 248 MB per
window comes from fresh context creation.

The next bounded diagnostic should use the exact qualified Core/Data and real
pyannote inputs to compare fresh versus reused encoder contexts. Record
`LastPoolAllocatedNewBytes`, `LastPoolReusedBytes`, allocation totals, generation
counts and `GC.GetTotalPauseDuration()` differences. Require unchanged tensor
bits, input identity and held-output ownership, and keep the existing cache
bound. Only then implement a request-scoped application successor and qualify
the full dialogue, meetings, cancellation and recovery. This work remains
separate from the frozen AMD queue. A diagnostic result is not an ORT speedup.

## Parakeet second

The exact [failed arithmetic timing trial](../../parakeet/arithmetic-comparison/results-20260921.md)
also retained allocation and collection counters for all **320 managed calls**,
including 240 measured calls. No rerun was necessary. The report's reference to
missing allocation attribution should be read precisely: totals exist; pause
durations and allocation sites were not captured.

| Role | Mean managed allocations per twenty-clip corpus | Measured calls without a generation-2 count increment |
|---|---:|---:|
| Production | 12.690 GB | 99 / 120 |
| Arithmetic candidate | 13.004 GB | 98 / 120 |

These allocation observations come from a trial whose timing controls failed.
They do not establish that the candidate is faster or slower. All four failed
clip controls and all their constituent requests are in
[summary-20260921.json](summary-20260921.json).

Two counterexamples show why collection counts alone are insufficient:

- Production worker 0, clip `1320-122612-0000`: the three measured requests
  take **8.3522680, 3.8501724 and 3.7659802 seconds**. Each reports collection
  differences `[3, 0, 0]` and approximately 765.16 MB allocated.
- Candidate clip `1188-133604-0001`, measured pass 3: worker 1 takes
  **5.8196108 seconds**, worker 4 **2.4018312 seconds**. Both report `[3, 0, 0]`
  and approximately 593.83 MB allocated, differing by only 1,296 bytes.

Equal counts do not imply equal GC pause durations. These observations neither
blame nor exonerate GC, the runtime or unrelated workstation activity. The cause
of the failed repeatability controls remains **unassigned**.

The earlier [complete graph trace](../../parakeet/performance-profile/results-20260921.md)
locates most allocation in the encoder:

| Trace pass | Frontend allocations | Encoder allocations | Decoder allocations | Encoder share |
|---|---:|---:|---:|---:|
| Unprofiled, 1,240 graph calls | 0.597 GB | 12.208 GB | 0.208 GB | 93.81% |
| Wall profile, 1,240 graph calls | 0.596 GB | 12.126 GB | 0.213 GB | 93.75% |

Each pass contains 20 frontend, 20 encoder and 1,200 decoder calls. All 2,480
graph observations and the separate twenty public controls are retained.
The trace retains graph outputs and includes small instrumentation allocations.
Its totals cannot be subtracted from a separate public run to calculate
application overhead. Encoder allocation is a useful later target, after pyannote.

## Counter semantics and validation

The original consumers call `GC.GetTotalAllocatedBytes()` without requesting
precise accounting. Differences are approximate process-wide managed bytes,
excluding native allocation. `GC.CollectionCount(generation)` differences
include older-generation collections, so the three columns must not be added
as independent events. Counters bracket the timed calls but are read separately
from the clock; they are not allocation stack traces or pause measurements.
The local .NET 10 reference documentation confirms these API distinctions and
the available cumulative pause-duration API.

[analyze.py](analyze.py) checks the four fixed closure identities and every
bound file, all raw integer clock intervals, original individual request rows,
monotone process counters and complete observation coverage. It recomputes all
sixty Parakeet clip controls with rational arithmetic and preserves
`attribution_valid:false`, `selected_for_amd:null`.
[verify.py](verify.py) independently checks every derived raw field, grouped
allocation/count totals and the seven qualified source files. Both pass.
