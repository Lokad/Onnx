# Request-scoped pyannote embedding contexts

The isolated Data candidate passes complete application qualification and
reduces cumulative managed allocations by 14.4% on the 30-second dialogue and
15.0–15.1% on two ten-minute meetings. Every normalized result equals its
predecessor. Both complete meeting timelines also equal Microsoft ORT exactly;
the largest centroid error is `8.9814e-7` against the unchanged `1e-4` bound.
These observations establish allocation reduction, not a matched speedup.

GB here means cumulative allocated bytes divided by `1e9`; it is not resident

observations come from the retained [matched ORT run](../optimized-ort/results-20260921.md)
and [complete meeting qualification](../optimized-meetings/results-20260921.md).
Historical times are not compared. The three single-window dialogue crops show
essentially unchanged allocation, as expected when no second window can reuse
the context.

## Change and scope

The [exact v3 patch](candidate-v3.patch) changes only embedding execution-context
lifetime. `Community1Diarizer.Diarize` creates an internal disposable request
around its embedding loop. Encoding and projection contexts are created lazily,
reuse their existing bounded pools across windows, and are discarded before
clustering. No context survives the public request. Default cache limits remain
128 MiB and 256 arrays; caller-visible results still own their storage.

The standalone `WeSpeakerEmbedder.Extract` instructions and public signatures
are unchanged. Explicit internal overloads preserve the old three-argument
entry point. Extraction and disposal use the existing owner lock. Cancellation,
invalid input, graph failure, interleaved requests, held outputs, input
preservation, disposal and subsequent recovery are covered by focused tests.

Core is byte-identical to the previously qualified convolution/LSTM candidate:
`469cb2d6a4558d917266434bd1f968c8b9f2762795b963800b2d945083852edd`.
Candidate Data is
`1d34666456a5da749dc3b40ee25621af0bed806c9167f3ad12e96d0736dca662`.
All 3,101 Core methods and 689 unrelated original Data methods match normalized
instructions. The changed methods are the diarizer and the compatibility
wrapper; additions are the request factory, four-argument extraction method
and request constructor/extraction/disposal methods. Arithmetic is unchanged.

The [ORT allocator inspection](ort-memory-review-20260921.md) explains the
relevant storage-lifetime difference from retained Microsoft source. It also
identifies unpooled convolution outputs as a remaining path to investigate;
it does not assign a measured allocation share to that path.

## Validation and retained failures

The final candidate passes both focused tests, 3,141 backend tests with 93
skips, and all 342 tensor tests. The byte-identical original application consumer
runs all 16 dialogue calls. The original meeting consumer runs both complete
ten-minute recordings and the recovery request. Input, output ownership,
held-result and native checks pass throughout. Retained exact meeting timelines
preserve ordinary/exclusive DER of 21.4593%/24.7763%; this run adds no new labels
or scoring convention.

Two earlier failures remain preserved. V1's synthetic test encoder averaged
already centered features, so the intended changing stimulus was constant:
one focused test passed and one failed. V2 corrected the stimulus to mean
squared features with silence and a changing signal. Both focused tests and
the backend suite then passed, but the tensor suite correctly rejected two
optional parameters. V3 replaces those defaults with explicit overloads. No
behavioral assertion, native tolerance or repository rule was weakened. Neither
failed predecessor reached a real-model public worker.

The v1 failure closure is
`6dcd75a7bf86f91bec262339253a132eb6a426d4277f9041f19b87addb40d71d`;
the v2 closure is
`8fde84f4d469ef392dae618c11530067458346df17dc80efed4d232fe73801b8`.
The older `candidate.patch` remains the failed optional-parameter version;
use `candidate-v3.patch` for the final source change.

All 3,401 resource samples pass; all 70 recorded PID/creation-time identities
are terminal. The largest sampled RSS across preparation, tests and applications
is 4,136,755,200 bytes, during the backend suite. The complete meeting worker
peaks at 1,808,900,096 bytes. Model workers use normal .NET 10.0.12 on Windows
i7-14700KF CPU 2. No VM worker or unrelated local process was changed.
