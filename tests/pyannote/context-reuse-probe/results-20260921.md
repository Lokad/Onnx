# Pyannote context reuse: allocation hypothesis passes

Reusing the existing bounded embedding context reduces repeated-call managed
allocations by **18.1–18.3%** in both process orders. All **108 graph calls and
17,502,642 output values** preserve the captured reference bits, including all
held outputs after later calls. All **213 resource observations** pass.

This admits a request-scoped pyannote application prototype under the
prospective allocation gate. It does **not** establish an application speedup,
change the Microsoft ORT comparison or promote a production change.

## Exact comparison

Windows i7-14700KF, CPU2 before CLR startup, normal .NET 10.0.12. Core
`469cb2d6a4558d917266434bd1f968c8b9f2762795b963800b2d945083852edd` and Data
`e7fe1668e3aa08fb07b1e5a687ef2b1e4af54567f6a458db09d411eb69f99aeb` are the
unchanged qualified convolution/LSTM candidate. Only the new diagnostic
consumer was built; no product assembly was rebuilt.

Each worker loads the same segmentation and embedding graphs, using their
original 32/64 MiB weight-packing budgets. Three real ten-second dialogue
crops supply the six captured graph inputs and output references. Every mode
runs three complete passes. Modes are:

- **Fresh:** a new default execution context for each graph call.
- **Reuse:** one default context per graph, reset between calls, retaining
  only already-released buffers within the existing 128 MiB/256-array cache.
- **No cache:** reused contexts with zero retained-buffer bytes, using the
  existing public `CreateExecution` overload.

Worker one runs fresh/reuse/no-cache; worker two runs no-cache/reuse/fresh.
No forced collection or runtime override is used. All first-pass observations
are retained separately. The following means include the six embedding calls
from passes two and three in each mode. MB means 1,000,000 bytes.

| Worker order | Mode | Managed allocations per call, MB | New tensor-pool payload per call, MB | Reused tensor-pool payload per call, MB |
|---|---|---:|---:|---:|
| Forward | Fresh | 204.304 | 38.658 | 31.959 |
| Forward | Reuse | 166.861 | 1.280 | 69.337 |
| Forward | No cache | 204.165 | 38.658 | 31.959 |
| Reverse | Fresh | 203.822 | 38.658 | 31.959 |
| Reverse | Reuse | 166.868 | 1.280 | 69.337 |
| Reverse | No cache | 204.155 | 38.658 | 31.959 |

The managed-allocation reduction is **18.327%** forward and **18.131%** reverse.
New pool payload drops by exactly **37,377,920 bytes per call** in every repeat
fixture. The remaining 1,280,000 new pool bytes equal the owned embedding output
payload `[1,2560,125]` of float32 values. Those outputs remain live and are never
recycled. The zero-cache control shows that merely keeping the context object
does not reproduce the buffer-reuse reduction.

Segmentation also preserves every output. Its new pool payload falls from
2,146,600 to 16,492 bytes per repeated call with reuse. The latter equals its
owned `[1,589,7]` output. The public diarizer already reuses segmentation
contexts within a request, so this is a diagnostic control, not a new
application optimization.

Substantial embedding allocation remains outside new tensor-pool payload.
This experiment does not identify those allocation sites or explain the
earlier Parakeet timing-control failures.

## Counters and limits

The measured interval includes context creation when applicable, reset and
graph execution. Model/input loading, tensor hashing, output validation,
retention and serialization are outside it. Precise process-wide allocation
snapshots, generation collection counts and cumulative pause-duration snapshots
are retained for every call, together with graph pool counters and integer clocks.

The six-call repeated embedding groups report **2.048–13.048 milliseconds** of
cumulative pause-counter increments, depending on worker and mode. These small
diagnostic totals do not assign GC's contribution to the complete public
application or to a different experiment. A completed collection may cross a
counter sampling boundary. Precise accounting, first-use effects and retained
outputs also make these unsuitable as matched application timings. All clock
observations, including the substantial order variation, remain in
[observations-20260921.json](observations-20260921.json).

The same guards apply to both workers: 10 GiB available-memory preflight,
8 GiB RSS, 900 seconds, at least 1 GiB available RAM and 20 GiB disk, and at
most 1 GiB output. The build uses the same owned-process monitor, permitting
compiler children. The reverse worker waited 30 seconds for its preflight;
neither worker was restarted or stopped.

| Process | Resource samples | Peak RSS, bytes | Exit |
|---|---:|---:|---:|
| Consumer build | 14 | 278,200,320 | 0 |
| Forward worker | 90 | 1,378,553,856 | 0 |
| Reverse worker | 109 | 1,227,706,368 | 0 |

All six recorded process identities, including the supervisor and compiler
children, are independently confirmed terminal. The consumer build retains
one platform-analysis warning for its affinity reporting call; execution is
explicitly restricted to Windows. No AMD workload or unrelated process was changed.

## Validation and next action

The independent Python auditor compares every saved output byte with the
captured references, checks complete mode/fixture order, raw counter arithmetic,
clock order, exact runtime/input identities, held-output/input checks and every
resource sample. A separate final read verifies all **343 closure file pins**,
all terminal identities and the exact output-payload allocation equality.

The next implementation should keep embedding encoder/projection contexts for
one `Community1Diarizer.Diarize` request, retaining their existing bounds and
releasing request references afterward. Preserve the standalone embedding API,
input validation, cancellation and owned output semantics. Qualify the original
public consumer, all dialogue fixtures, two complete meetings and recovery
before seeking matched application improvement. Keep the frozen AMD candidates
unchanged; this would be a separate successor.
