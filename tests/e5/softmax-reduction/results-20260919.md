# Masked-softmax reduction: local exactness proof

The candidate preserves all exercised output bits and removes the targeted
repeated vector stores in captured optimized loop code. **There is no timing
result or product change.** [Source and reproduction](README.md),
[complete proof records](proof-20260919.json).

The actual AMD product capture first identified the mechanism: the inlined
maximum helper stores a full vector on every variable-index lane read, both
for the maximum and for NaN validity. ORT's pinned MLAS source uses register
reductions. The prototype keeps Lokad's exact ordered comparisons and changes
only their final lane access and validity test. It does not adopt ORT's
different maximum semantics or combine this change with zero-block skipping.

Three finite Windows processes each passed the same checks:

| Check | Cases per process |
|---|---:|
| Direct maximum, copied and candidate versus actual frozen core | 109,488 |
| Complete tensors with scalar/SIMD, offsets and guards | 1,728 |
| In-place outputs | 3,456 |
| Short-mask refusals preserving output | 3 |

Both inputs and masks remain unchanged. Exceptional inputs include NaN
payloads, infinities, signed zeros, overflowed additions and fully masked rows.
The maximum independent double-normalization error is `2.477703762160388e-7`
at the unchanged `1e-6` diagnostic limit. The host uses .NET 10.0.12, eight-lane
vectors and inherited logical CPU 4. Scalar execution is exercised explicitly;
other hardware vector widths are not qualified.

The initial short run and two conditioning captures are all retained. No
capture contains the final full Tier1 methods. The last capture does contain
optimized paired-row loop bodies (Tier1-OSR, entry `0x262`): original 4,030
bytes, candidate 4,234 bytes. Original blocks IG47/58 and IG77/87 repeatedly
store `ymm0` to read a scalar lane; IG51/81 store `ymm1` for each validity lane.
The candidate uses literal register extracts/shuffles and ordered scalar
comparisons, plus `vptest` in IG36/74. Those vector stack-store loops are absent
from the candidate's paired-row reductions. The larger code size and remaining
unqualified final-tier behavior require measurement; instruction inspection
does not establish a speedup.

All three children were independently verified terminal. Sampled peaks were
54,407,168, 56,299,520 and 56,233,984 bytes. These arithmetic-only runs used CPU 4
while the separately supervised Whisper comparison used CPU 2; their finite
activity is part of the active-workstation context, not an exclusive-host
timing claim. An initial launch with the system Python failed to import
`psutil` before a child was created; the documented existing environment
contains that dependency.
