# Disabled-profiler allocation: locally qualified candidate

An isolated graph-execution change removes a median **55,520 allocated bytes
per e5 request** in nine of ten unprofiled case/policy combinations. It avoids
creating a closure and delegate for each of the model's 347 nodes. All 1,920
complete executions retain identical output bits and profile descriptions.
This is allocation evidence on Windows, not an AMD latency improvement or a
production promotion.

## Mechanism and source inspection

`ComputationalGraph.RunCoreInner` constructs a captured `Func<string>` before
`ProfilerContext.StartNodeProfile` checks whether profiling is enabled. The
callback supplies node input shapes and types. Disabled and wall-only profiling
discard it after the caller has allocated it.

The candidate uses the existing execution profiler's `Enabled` and `WallOnly`
state. Only the detailed branch declares and captures a local copy of the node;
the other branch calls the existing callback-free overload. Capturing the
original foreach variable outside that lexical branch would leave the closure
allocation in the unprofiled path. No operator arithmetic, API, option or
production dispatch changes in this experiment.

The pinned ORT 1.23.2 source at
`a83fc4d58cb48eb68890dd689f94f28288cf2278`,
`onnxruntime/core/framework/sequential_executor.cc:347`, guards node-name and
input-shape profiling work with `Profiler().IsEnabled()`. This is a source
comparison; it supplies no native timing measurement.

Compiled-code checks establish that the archived baseline has identical
normalized IL, operands, locals and exception clauses for all **3,086** core
methods compared with the qualified `d1f86a7346dc` product. Exactly two candidate
methods differ: `RunCoreInner` and its generated detail callback; the remaining
3,084 methods are identical. In the candidate, IL branches at offsets 681 and
690 skip to 750 when profiling is disabled or wall-only, bypassing closure and
delegate constructors at offsets 692 and 738. The audit rejects other branch
entries into this interval. Actual allocation measurements confirm the effect.

## Complete e5 allocation results

Windows i7-14700KF, logical CPU 2, .NET 10.0.12, normal GC/tiering, one CLR
processor and no runtime overrides. Two fresh sequential processes use the
same compiled consumer, one with each core. Each covers all five inputs, both
Default and Memory policies, and disabled/detailed/wall profiling. Every group
has 16 warmup and 16 observed calls: 960 warmups and 960 observed calls total.

The table gives median `LastAllocatedBytes`, which covers graph execution.
Public-call allocation is independently recorded and shows the same reduction.
Bytes are per request, and include caller-owned outputs.

| Input | Policy | Baseline bytes | Candidate bytes | Median paired saving |
|---|---|---:|---:|---:|
| 8 tokens | Default | 1,289,632 | 1,234,112 | 55,520 |
| 8 tokens | Memory | 678,288 | 622,768 | 55,520 |
| 30 tokens | Default | 3,047,520 | 2,992,000 | 55,520 |
| 30 tokens | Memory | 814,160 | 758,640 | 55,520 |
| 30 padded to 128 | Default | 10,877,632 | 10,822,112 | 55,520 |
| 30 padded to 128 | Memory | 1,410,976 | 1,349,984 | 60,992 |
| 128 tokens | Default | 10,864,600 | 10,809,080 | 55,520 |
| 128 tokens | Memory | 1,405,504 | 1,349,984 | 55,520 |
| 512 tokens | Default | 41,548,408 | 41,492,888 | 55,520 |
| 512 tokens | Memory | 3,778,152 | 3,722,632 | 55,520 |

Every observed disabled/wall pair allocates less under both boundaries. All
ten wall-profile groups also have a 55,520-byte median saving. The common
55,520-byte reduction is 160 bytes per node. The additional saving in the
padded Memory group is not attributed to callback removal; its allocation
counts vary, and every sample remains in the retained evidence. Detailed
profiling retains its callbacks and has median differences near zero
(-168 to +288 bytes). No allocation value is converted into a latency claim.

## Correctness and qualification

All original and candidate output hashes, node IDs/operators, input shape/type
details, profile stages and wall-profile identities agree across all calls.
Every native numerical check passes the unchanged `1e-4` limit; maximum scaled
error is `1.6391277313232422e-6`. Inputs and held outputs survive execution and
Reset. The audit independently recomputes native comparisons for all 120
saved first/last full arrays and binds every other call by its exact hash.

The candidate passes **3,101 backend tests (93 skipped)** with test collections
serialized, and **342 tensor tests**. Existing nested wall-profile, concurrency,
exception and lifecycle tests are included. Core bytes remain identical to the
core exercised by the e5 consumer after the test builds.

Two failed qualification attempts are retained. The first omitted the isolated
CLI build and produced 51 CLI-test failures (3,044 passed, 99 skipped). After
building the CLI, one test failed while reading the process-global
`OnnxImport.LastErrorCause` (3,100 passed, 93 skipped). It passes in isolation
and in the complete serialized suite. Source inspection shows unrelated import
calls clear that shared diagnostic; the failure is consistent with parallel
test interference. The exact interfering call was not captured. No inference
or numerical failure was hidden or rerun, and the profiler candidate was not
changed during these corrections.

Separately, `PackedWeightBudgetTests` now uses the repository's existing
`SequentialLogSink` collection, as the other import-diagnostic tests already
do. This prevents unrelated test collections from clearing the diagnostic
between the import and assertion. The normal production-tree backend run then
passes all 3,101 tests with 93 skips, without serializing the whole suite.
Its logs are retained in `artifacts/e5-profiler-test-isolation-20260921`.

## Evidence and next action

Both inference workers and their supervisor are terminal. All 761 resource samples
pass; peak RSS is 3,545,341,952 bytes. Limits were 1,800 seconds per worker,
8 GiB RSS, 10 GiB available RAM before launch, 1 GiB remaining available RAM,
and 20 GiB free disk. Baseline/candidate workers finished in approximately
99/98 seconds; those durations include validation and are not latency results.
