# E5 projection activation packing — 2026-09-19

The candidate is rejected for product integration. All correctness and resource checks pass, and duplicate controls satisfy the prospective stability limits, but including activation copying makes the thirty-row bank **3.18% slower** and the 128-row bank **4.14% slower** than the first control. Every worker regresses both primary banks. No production kernel, default or numerical tolerance changes.

## Mechanism and complete cost

Each twelve-row activation group is copied into contiguous reduction order, so the twelve scalars consumed in one step are adjacent. The existing row partition, 32-column weight format, accumulating destination, FMA order and eight/three/two-row tails are retained. Every candidate call rents scratch, copies all main-group activations, computes and returns scratch. Destination clearing is timed for every mode. Constant-weight packing is outside all steady-state measurements. The two controls invoke the same original kernel and share the same packed weights.

The fixed experiment ran four fresh processes in orders 1/2/3/4 on the AMD EPYC 9V74, logical CPU 2, .NET 10.0.8, normal tiering/GC and no runtime overrides. A fifth process captured generated code separately. Each worker was bounded prospectively by 2 GiB sampled group RSS, 1,200 seconds and 256 MiB available memory. The bank has 72 matrices and 84,934,656 packed bytes, with two complete bank warmups and seven retained samples per mode. Inputs are synthetic and independent; this is not complete e5 execution or an ORT comparison.

## Actual AMD instructions

Both compute loops contain 24 FMAs, 12 broadcasts and 2 full-vector weight loads per reduction step, with no vector stack accesses or loop calls. The candidate removes all four scalar stack accesses in the original hot loop, but the intended literal input displacements do not survive compilation. The JIT separately computes and sign-extends each `j * 12 + row` index.

| Compute method | Code bytes | Hot scalar stack accesses | Hot `movsxd` | Hot `lea` |
|---|---:|---:|---:|---:|
| Kernels.PackedTile12 | 1135 | 4 | 2 | 1 |
| InputPacked.PackedTile12 | 1009 | 0 | 13 | 12 |

The packing method is a separate 415-byte FullOpts body. The compute bodies are FullOpts too; no tiering-disabled counterfactual is used. The literal-displacement portion of the code-generation requirement therefore remains unmet even though scalar reloads disappear. Copying and generated index work both remain in measured cost; this experiment does not isolate their contributions or prove that every possible activation-packing implementation loses. A future pointer-based design would need a new prospective proof and comparison, not reinterpretation of these results.

## Correctness, ownership and evidence

Each timing worker passes 256 finite/exceptional geometries, 54 complete packing-layout cases and 8 invalid-shape refusals. Four workers total 1,024 geometry checks, 216 packing checks and 32 refusals. Full output bits match the original on nonzero and repeated accumulation; independent scalar-FMA coordinates agree. All original inputs, prepared weights and offset guards survive unchanged. Packing preserves raw float bits, including NaN payloads. The local AVX2 host passes the separate 54-case layout proof and correctly refuses unsupported AVX512 computation. Four audit tests cover the prospective decision, unstable controls, a single-worker regression and eight malformed sample/coverage variants.

All five workers exit zero. Peak sampled timing-worker RSS is 231.961 MB, with all 220 resource samples retained. Code capture finishes in about 0.12 seconds with only one resource sample, so its sampled RSS is not a useful lifetime peak.
