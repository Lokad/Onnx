# Projection benchmark compilation interference — 2026-09-19

The projection harness queued background compilation of its own JSON validation
and sample-list growth code into later timed calls. The corrected harness checks
the same pinned panel directly and preallocates each seven-sample list. A separate
confirmation run removes those specific compilation events under normal tiering,
with every arithmetic and storage check preserved.

This fixes a measurement problem. It does not establish an e5 inference speedup,
promote the earlier overwrite candidate, or make historical timing failures pass.

## What the runtime events show

The previous [overwrite experiment](../packed-overwrite-20260919.md) found one slow
thirty-row mode block in each worker, without recorded GC. A new diagnostic used
the same arithmetic and workload, adding exact call markers and CPU counters.
An external collector recorded JIT/GC events on CPU 0 while the target remained
on CPU 2: AMD EPYC 9V74, .NET 10.0.8, SDK 10.0.204.

The collector follows Microsoft's [DiagnosticsClient/EventPipe API](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/diagnostics-client-library)
and captures [tiered compilation events](https://learn.microsoft.com/en-us/dotnet/fundamentals/diagnostics/runtime-tiered-compilation-events).
Runtime timestamps are matched to the independently saved Stopwatch boundaries,
using bounded custom-marker emission times. All eight traces across the two
campaigns have zero reported loss and no unmatched JIT starts.

Three slow measured bank calls in the first diagnostic have direct event evidence:

| Order / mode / sample | Wall ms | Foreground-thread CPU ms | Observed overlapping compilation |
|---|---:|---:|---|
| 0 / overwrite+clear / 5 | 22.101 | 14.282 | JSON writer, ASCII and runtime helpers |
| 0 / overwrite+clear / 6 | 28.186 | 14.268 | JSON serialization; 13.582 ms overlap with `ObjectDefaultConverter.OnTryWrite` compilation |
| 5 / overwrite without clear / 5 | 15.262 | 12.886 | `List<double>.AddWithResize`, `Grow`, `GetNewCapacity`, `set_Capacity` |

These are different runtime threads in the same target process. No GC events
overlap these calls. Compilation elapsed time includes scheduling and is not
itself CPU time. CPU counters bracket the timed interval, so they are supporting
observations rather than an exact decomposition of wall time.

The first fixed schedule used two orders, tracing on/off, and normal tiering
versus the diagnostic `DOTNET_TieredCompilation=0` counterfactual. The same
instrumented binary ran in every condition. The predeclared slow-sample threshold
was 15 ms, taken from the earlier observation.

| First diagnostic condition | Workers | Workers with a slow 30-row sample | Slow samples / 70 | Maximum ms |
|---|---:|---:|---:|---:|
| Normal tiering, untraced | 2 | 1 | 1 | 18.199 |
| Normal tiering, traced | 2 | 2 | 3 | 28.186 |
| Tiering disabled, untraced | 2 | 0 | 0 | 13.914 |
| Tiering disabled, traced | 2 | 0 | 0 | 13.571 |

The evidence supports background compilation consuming CPU during the observed
slow samples. It does not attribute every older untraced outlier. Small-row
kernel tier transitions also occur elsewhere, including warmup and some measured
intervals; the investigation does not justify changing their production
optimization attributes to fix the JSON-related delays.

## Correction and separate confirmation

`PackSet` previously serialized the same panel object five times to compare its
hash property. `Verify()` now checks exact shared-reference identity, stable
addresses, guards and complete hashes directly. Each seven-sample list is
constructed with capacity seven. No kernel, clear operation, arithmetic order,
geometry, sample count or correctness check is removed.

Eight new workers compared the original and corrected harness under normal
tiering, again using orders 0 and 5 and both tracing states. All samples remain.

| Confirmation condition | Workers | Slow samples / 70 | Maximum 30-row ms |
|---|---:|---:|---:|
| Original, untraced | 2 | 7 | 27.302 |
| Original, traced | 2 | 0 | 14.846 |
| Corrected, untraced | 2 | 0 | 13.429 |
| Corrected, traced | 2 | 0 | 14.658 |

The traced controls still compile JSON code during measured intervals, although
the bursts shift to isolated 128/512-row measurements in this confirmation.
This movement is why the absence of a slow thirty-row sample alone is insufficient.

| Traced confirmation visit | JSON compilation overlap with measured intervals, ms | `List<double>` growth compilation overlap, ms |
|---|---:|---:|
| Original, order 0 | 115.208 | 4.946 |
| Original, order 5 | 135.696 | 4.533 |
| Corrected, order 0 | 0 | 0 |
| Corrected, order 5 | 0 | 0 |

The corrected traces still contain 7.295 and 7.386 ms of kernel JIT overlap with
measured intervals, plus 43.620 and 53.353 ms from other methods across the whole
schedule. Thus the correction removes the demonstrated scaffold problem; it does
not prove that every sample is free of compilation or establish fine timing
calibration. The original overwrite candidate's failed 128-row promotion screen
is unchanged. A future performance decision needs its own prospective protocol.
