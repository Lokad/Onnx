# Short e5 ends before final matrix-dispatch optimization is observed

Reinspection of the retained runtime events identifies a narrower lead for the
short-e5 release blocker. In all four eight-token processes, both
`Tensor<float>.RunFloatMatMulKernel` and `RunBatchedFloatMatMul` load initial
`QuickJitted` code, then `QuickJittedInstrumented` code. Neither method has an
`OptimizedTier1` load in those complete traces. Both methods reach that final
tier in all four 512-token processes.

The intermediate matrix-dispatch loads occur at short-input calls 488, 484,
493 and between calls 505 and 506. A load outside a call is retained rather
than discarded because its earlier association used `call=-1`. Each timeline
binds one runtime MethodID and signature, and retains the complete original
events, including native addresses and raw bytes. All eight compressed event
exports match the closed capture's hashes and event counts; selected events
also match the previously published observations. No inference was repeated.

The .NET 10.0.8 source explains why call count alone does not specify this
state. Its tier manager can promote ordinary IL from the initial quick tier
to an instrumented quick tier before final optimization. An observed
`QuickJittedInstrumented` load therefore is not final optimized code.
[Tier selection source](https://github.com/dotnet/runtime/blob/v10.0.8/src/coreclr/vm/tieredcompilation.cpp#L253-L285).

The release defaults set a 100 ms call-counting delay and a single-processor
multiplier of ten. Configuration applies that multiplier when the process sees
one CPU, as these workers do. The tier manager can extend delay during new-method
activity. These defaults explain a possible elapsed-time dependency; they do
not prove the installed process's effective delay or explain every latency change.
[Defaults](https://github.com/dotnet/runtime/blob/v10.0.8/src/coreclr/inc/clrconfigvalues.h#L428-L454),
[single-CPU configuration](https://github.com/dotnet/runtime/blob/v10.0.8/src/coreclr/vm/eeconfig.cpp#L609-L623),
[delay extension](https://github.com/dotnet/runtime/blob/v10.0.8/src/coreclr/vm/tieredcompilation.cpp#L530-L552).

This evidence applies to the older release/M73 diagnostic products. The newer
M78 failure and current direct-depthwise candidate are different assemblies;
these events cannot be attached to their clocks. Code-loading events also do
not attribute execution time to a version. The original failed comparisons
remain failed, with all calls and thresholds unchanged.

The next e5 investigation should observe these exact method identities and
runtime state on the actual candidate after the active Parakeet comparison.
Retain the original 780-call window and, if extending observation, label the
extension separately and choose its bound before capture. Test whether the
intermediate-to-final transition occurs and whether timing changes coincide.
Do not sweep JIT flags, annotate product methods, infer a settled tail score,
or change release warmup from this older observation alone.
